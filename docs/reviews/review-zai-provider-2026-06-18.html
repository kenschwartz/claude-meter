What was built

A new z.ai provider for the macOS menu-bar meter, made the default backend. z.ai's /api/monitor/usage/quota/limit is decoded into the existing UsageResponse shape:
  • TOKENS_LIMIT unit=3 number=5 → five_hour (5-hour token limit)
  • TOKENS_LIMIT unit=6 number=1 → seven_day (weekly token limit)
  • TIME_LIMIT → extra tools_5h
  • data.level → plan label ("max" → "GLM Max")
Token read from GLM_API_KEY in ~/.hermes/.env (mirrors the zai shell launcher). Claude kept behind a config flag.

Findings (all NOTE)

NOTE · src/providers/mod.rs · REJECTED. The |_|| in the z.ai credential-error path discards the CredentialError variant. The reviewer suggested format!("[cred] ... {e}"), but that would embed CredentialError::NotFound's Display, which is the Claude-specific text "Claude Code credentials not found in ~/.claude/.credentials.json" - wrong for z.ai. The current clear z.ai message is more accurate, and read_zai_token only ever returns NotFound today. No change.
NOTE · src/providers/zai.rs · REJECTED. detected_plan() could return a bare Claude name if z.ai ever returned a raw "max" level. Non-issue: the adapter always GLM-prefixes via format!("GLM {}", title_case(level)), so the "max"/"pro" literal arms in detected_plan() are never reached for z.ai. Reviewer confirmed "the guard works." No change.
NOTE · src/credentials.rs · APPLIED. The ~/.hermes/.env parser silently skipped GLM_API_KEY = token (whitespace around =). For a long-running GUI meter a silent "token not found" on a whitespace variant is poor UX. Fix applied: split on the first = and trim both sides (a strict superset of the KEY=value shape, also rejecting look-alike keys like GLM_API_KEY_BACKUP). Extracted glm_api_key_from_contents() and locked it with a regression test covering whitespace, quotes, look-alikes, and last-match-wins.
