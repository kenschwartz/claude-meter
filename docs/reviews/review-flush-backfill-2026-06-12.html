Detailed findings

A. detect_live_flush correctness

Consumed-by-usage (src/macos_app.rs:371): The scan from the flush index inclusive correctly catches any reading where util >= stop_at_percent. The flush reading itself is checked, handling the drop-landing-high case (90% → 70%). Tested.

Anchor-advanced (src/macos_app.rs:374): The consumed scan compares each later reading’s resets_at against the flush reading’s. When the anchor jumps forward by more than anchor_tolerance_seconds, the party is ended. The function reset_delta_seconds(a, b) = a - b; the flush_reset is b and each later reset is a, so a positive delta past the tolerance means the anchor advanced. This direction is consistent with update_celebration at line 271. Tested.

Off-by-one on slice bound (src/macos_app.rs:370): The slice readings[idx..] starts at the flush reading itself. This is correct: the flush reading’s util IS checked against stop_at_percent (catches drop-landing-high), and the flush_reset vs itself comparison yields delta 0 (within tolerance). No off-by-one.

Latest-flush-wins (src/macos_app.rs:354-363): Each flush match overwrites flush_idx, so the later flush always wins. The consumed scan then only looks from that later flush onward, ignoring an earlier consumed one. Logic is sound, but untested (see Follow-up 1).

B. backfill_celebration wiring

Not clobbering in-flight parties (src/macos_app.rs:389): The early return when load_celebrate_state(exe_dir).active is true correctly prevents the backfill from overwriting the since timestamp of an ongoing party.

.expect safety (src/macos_app.rs:399-401): detect_live_flush only returns Some(idx) when readings.len() >= 2 (guard at line 340). The invariant is proven: the Vec is immutable within the if let block, so readings.last() is necessarily Some. No panic path.

Seed → poll interaction: Traced the full cycle. The backfill seeds CelebrateState { last_util, last_reset, active: true, since }. The next poll_once call enters update_celebration, loads this state, and checks end conditions against the fresh API response. The post-flush utilization is near 0, so no false re-detection. A subsequent anchor advance or usage climb properly ends the party. Tested indirectly via the unit tests on detect_live_flush, though not end-to-end.

C. DB query

Parameterized: ?1 is metric, ?2 is "-{days} days". No injection vector. Window: datetime(’now’, ?2) with "-8 days" gives readings from the past 8 days. 8 days is a 1-day buffer on the 7-day reset window, which is reasonable for a startup backfill. The autovacuum keeps 30 days of history, so nothing is missed even for longer downtime within reason.

dead-code attribute: #[cfg_attr(windows, allow(dead_code))] on query_recent_readings allows the unused function warning only on Windows, where macos_app.rs does not exist. Correct.

D. Framework audit

Consistency with update_celebration: Both paths decompose into the same helpers: is_flush and reset_delta_seconds. The advanced closure in detect_live_flush (lines 344-350) is a near-verbatim copy of the anchor-advance check in update_celebration (lines 270-275). Both compute reset_delta_seconds(cur, prev) and compare against cfg.anchor_tolerance_seconds with strict >. Both treat parse failures as "not advanced" (unwrap_or(false)). No divergence identified.

Re-party risk: There is no user-facing "dismiss party" action in the codebase, so the question of ignoring dismissal does not apply. After natural consumption (usage climbed back above stop_at_percent, or a scheduled reset advanced the anchor), detect_live_flush returns None. The backfill cannot resurrect a consumed party. Verified by the _consumed_by_usage and _ended_by_scheduled_reset tests.

E. Tests

6 new tests, all meaningful and non-vacuous:

  • test_detect_live_flush_active — happy path, 2 readings, returns Some(1)
  • test_detect_live_flush_consumed_by_usage — 3 readings, post-flush usage climbs to 8% (above 5% stop)
  • test_detect_live_flush_ended_by_scheduled_reset — 3 readings, anchor jumps from A to B
  • test_detect_live_flush_no_flush — small rise (3% → 4%), no detection
  • test_detect_live_flush_drop_landing_high_is_not_party — 90% → 70% is not a party
  • test_query_recent_readings_ordered — DB query oldest-first, filters metric correctly

Not covered (see Follow-ups):

  1. Two flushes in the same window — the "latest flush wins" branch has no test.
  2. Exactly-at-stop_at_percent boundary (5.0% util) — code uses >=, no test validates.

F. Conventions

No em dashes. No magic numbers that warrant a config tunable (the 8-day window is a reasonable default). snake_case naming throughout. i18n wrapper not needed here (log lines only).

Follow-ups

1. Add test: two flushes in the same window
src/macos_app.rs:354-363
The loop always overwrites flush_idx on each match, so a later flush supersedes an earlier one. This is correct from reading the code but has no test. Add a test with readings like [54%, 0% (A), 3% (A), 0% (A)] — two flushes at idx 1 and 3, should return Some(3). Also test the case where the earlier flush was consumed and the later one is clean: [54% (A), 0% (A), 8% (A), 0% (A)] → should return Some(3), not None.
2. Add test: exactly-at-stop_at_percent boundary
src/macos_app.rs:371
The consumed scan uses >=. Add a test where post-flush utilization is exactly 5.0 with stop_at_percent = 5.0, verifying the party does not start. Also confirm that 4.999 does start the party (it slips under the threshold by epsilon). This documents the boundary behavior.

Neither issue is a correctness bug; both are test-coverage gaps. Resolve before the feature branch merges to main.
